### 4.3 两个必须写死的存储约定（否则后期数据不可用）

**① `price_period` 存「当月 1 日」**

`fields.Date` 存的是完整日期，但业务语义是月份。若不统一，同一个 2026-03 会存成 3/5、3/18 等各种值，**分组和排序直接崩**。

| 环节 | 处理 |
|---|---|
| 写入 | 解析出 `YYYY-MM` 后统一补 `-01` 写入（如 `2026-03-01`） |
| 显示 | 视图 `options="{'max_precision':'months'}"` 月份选择（只选年月、不选日）；列表/导出显示 `YYYY-MM` |
| 分组/排序 | 直接按日期列分组（同月自然同值） |
| 空值 | 允许为空，统计时归入「未标注价格期」 |

**② `item_code` 一律按文本处理（Excel 数字陷阱）**

国标清单编码是 **9 位纯数字**（如 `010101001`），结构为**前6位统一编码 + 后3位分项码**：

| 位置 | 含义 | 示例 |
|---|---|---|
| 第1-2位 | 专业工程顺序码 | `01`=房屋建筑与装饰，`03`=通用安装工程 |
| 第3-4位 | 附录分类顺序码 | `01`=土石方工程 |
| 第5-6位 | 分部工程顺序码 | `01`=土方工程 |
| 第7-9位 | 分项工程顺序码（全国统一） | `001`=平整场地 |

> **注意**：系统支持 9位 和 12位 两种编码输入——规范文件为9位，实际工程常含后3位自编顺序码。入库保留完整编码用于溯源，匹配时统一取前9位。

**Excel 数字陷阱处理**：

openpyxl 读数值型编码会丢失前导0或转科学计数法，处理规则：

| 单元格类型 | 处理规则 |
|---|---|
| `str` | 原样去空白；**长度=12位且纯数字则截取前9位**，**长度=11位且首字符≠0则左侧补0成12位再截取前9位**（可能是12位丢失前导0），其他情况标警告并原样入库 |
| `int` / `float` | 先转字符串，再按上面规则处理 |
| 长度 = 10 且为数字 | **提示规范文件录入错误**（多了一位0），建议修正为 9 位；暂按原值入库但标 warning |
| 长度 ≠ 9 且 ≠ 11 且 ≠ 12 且非纯数字 | **不报错**，标「警告-编码格式异常」，原样入库（老清单常有自定义编码） |

> **为什么支持11位编码**：用户实际工程中可能有12位编码（含自编顺序码），但导入时前导0可能丢失（如 `010101001001` → `10101001001`）。系统识别11位纯数字编码且首位≠0时，自动补前导0恢复为12位，再截取前9位用于匹配。`item_code` 存规范化后的完整值（补0后的12位或原9/12位），`item_code_raw` 始终保留单元格原始字符串。

### 4.4 金额精度：为什么 `Float` 够用（避免日后误判）

Odoo 的 `fields.Float` 在 PostgreSQL 中是 **`double precision`**（不是 `numeric`），这一点必须先讲清楚，否则"PG numeric 精确"的说法会让人误以为金额列也是精确存储。

| 项 | 结论 |
|---|---|
| double precision 有效数字 | 约 **15–17 位十进制** |
| 本项目最大量级 | 单条合价约 **10⁸–10⁹ 元**（亿元级工程的分项合价） |
| 需要的有效数字 | 合价 10⁹ 元 × 分位（10⁻²）= **12 位** |
| 余量 | 12 < 15，**安全，且有余量** |
| 极端边界 | 若单条合价超过 **10¹³ 元**（十万亿），需改 `numeric` —— 记为风险 **R5**，当前不会发生 |

**因此保留原设计，但明确三条纪律**：
1. **算术一律在 Python `Decimal` 中做**（尤其合价校验 `工程量 × 单价`），算完再写回 Float，误差量级 < 1e-9，不影响分位；
2. `Char` 文本列保存**原始字符串**（`"1,234.50 元"` 原样），审计时可逐字对账——这是"数据禁编造"的可追溯基础；
3. 排序/聚合/比较**一律用 `_num` 数值列**，绝不对 `Char` 列做数值运算。

### 4.5 复合索引：声明式 `models.Index` / `UniqueIndex`（v3.8 定稿）

Odoo 字段的 `index=True` 只支持单列，四个复合索引须另建。**v3.8 起采用 Odoo 19 内置的声明式索引**——在模型类上声明 `models.Index('(col1, col2)')` / `models.UniqueIndex(...)`（属性名以 `_` 开头），**安装、升级两条路径都由 ORM 自动维护**，无需手写 SQL、`post_init_hook` 或 `migrate` 钩子。

```python
_item_code_unit_idx = models.Index('(item_code, unit)')
_biz_id_unique_idx  = models.UniqueIndex('(biz_id)', message='biz_id 冲突')
```

**四条复合索引**：`(item_code, unit)`、`(project_name, sequence)`、`(province, price_period)`、`(import_batch_id, sequence)`。

> **方案演进（历史，勿再采用）**：v1 用 `post_init_hook` 建索引（仅安装执行一次，升级不跑，会静默退化）；v6.2 改为 `post_init_hook`（安装）+ `migrate` 钩子（升级）双入口。二者均被 v3.8 声明式索引取代——`models.Index`/`UniqueIndex` 由 `odoo.models` 从 `odoo.orm.table_objects` 重导出，M1.1 已在 `boq_item`（四条复合 + `biz_id` UniqueIndex）、`import_batch`、`material_dict`、`audit_log` 全部声明式落地，见 §17。

### 4.6 `_parent_store` 的取舍（性能）

`_parent_store=True` 会维护 `parent_path` 字段（**Odoo 19 须显式声明 `parent_path = fields.Char(index=True)`，不再自动补齐，且不接受 `unaccent` 参数**），读层级飞快，但**每次写入都要更新祖先路径**——M2 一次导入几千行清单时会被拖慢。

| 模型 | 数据量 | 读写比 | 决定 |
|---|---|---|---|
| `material.dict` | 小（百~千级） | 读多写少 | ✅ **启用** `_parent_store` |
| `boq.item` | 大（万~十万级） | 批量写多 | ⚠️ **M1 暂不启用**；靠 `import_batch_id + sequence` 已在 M2 够用。若 M3 层级视图确有性能问题，再单独评估 |

### 4.7 数据性质与同类项聚合键【v3 新增】

**① `data_source_type` —— 防止统计污染（P0）**

场景 2「导入待审清单做审计」若与"已完工程真实单价"混在一张表里，`AVG(unit_rate)` 会被未定稿报价污染，且误差会随轮次放大。

| 规则 | 落地 |
|---|---|
| 默认域 | 所有统计口径的**默认 domain** 必须含 `('data_source_type','=','completed')` —— 写在 `boq_item` 的**统计方法**里，不是写在视图里（防遗漏） |
| 待审批次 | 导入向导选 `pending_review` 时，界面明确提示"本批不计入历史均价" |
| UI 义务 | 任何均价展示**必须同时显示样本数 + 数据性质构成**，禁止出现无口径说明的均价 |
| **导入强制【v3.1 → v6.5 强化】** | 导入向导**必须显式要求选 `data_source_type`，UI 不得预填**；未选则**阻断入库**。模型层 `data_source_type` **`required=True` 且无默认值**——任何 create 必须显式带值，模型层直接拒绝「未设值」写入（双保险，详见 架构 §4.8）。理由：若仅靠向导约定，任何绕过向导的写入（API / 批量脚本 / 夹具）会落到默认值把待审/控制价混进历史均价 |

**② `match_key` + `match_key_source` —— 让「什么算同一项」成为一等公民（P1，M1 建字段）**

v2 里"同类项"散落在 `item_code+unit` / `std_*` / `material_dict_id` 三处，没有优先级，M3 必然踩坑。M1 建计算字段并固定优先级：

```
# 已知 10 位异常编码映射（规范录入错误，多一位 0）→ 修正为 9 位
# 经核对 2013/2024 规范文件：仅以下 2 例，未发现的 10 位一律原值入库 + warning
GB_CODE_10D_ANOMALIES = {
    '0302280006': '030228006',   # 重整器
    '0304130010': '030413010',   # 小区路灯
}

compute_match_key():
  # 步骤1：标准化编码（处理11位/12位/10位异常）
  code_9, code_full = parse_gb_code(item_code)
  
  ver = item_code_version or 'unknown'   # 【F1】版本维度，默认 unknown

  # 步骤2：按优先级计算匹配键
  if material_dict_id:            return f"dict:{material_dict_id.id}|{unit_std}",  'dict'
  elif std_name and std_spec:     return f"std:{std_name}|{std_spec}|{unit_std}",   'std'
  # 【F3】2024 版总图工程 Z 前缀编码：强制 version=2024，单独成键
  elif code_9 and code_9[0] == 'Z':
                                  return f"code:2024:{code_9}|{unit_std}",          'code'
  # 【F1】国标 9 位码：带入版本维度，2013 与 2024 同码不再误聚合
  elif is_valid_gb_code(code_9):  return f"code:{ver}:{code_9}|{unit_std}",         'code'
  # 【F1】兜底：名称聚合也带入版本维度
  else:                           return f"raw:{ver}:{norm(item_name)}|{norm(item_feature)}|{unit_std}", 'raw'

def parse_gb_code(code):
    """解析国标编码，返回 (code_9, code_full) 元组"""
    code = str(code).strip()
    
    # 情况1：12位编码 → 截取前9位，完整保留
    if len(code) == 12 and code.isdigit():
        return code[:9], code
    
    # 情况2：11位编码 → 可能是12位丢失前导0 → 补前导0 → 截取前9位
    elif len(code) == 11 and code.isdigit() and code[0] != '0':
        code_padded = '0' + code  # 补前导0
        return code_padded[:9], code_padded
    
    # 情况3：9位编码 → 直接使用
    elif len(code) == 9 and code.isdigit():
        return code, code
    
    # 情况4：10位编码 → 规范文件录入错误（多一位0）
    #   【F2 裁决】已知异常→按映射修正为 9 位；未知→原值入库 + warning，匹配退化为 raw
    elif len(code) == 10 and code.isdigit():
        if code in GB_CODE_10D_ANOMALIES:
            corrected = GB_CODE_10D_ANOMALIES[code]   # 修正为 9 位
            return corrected, corrected               # item_code 存 9 位，原 10 位留 item_code_raw
        else:
            return code, code                          # 原值入库，匹配时 is_valid_gb_code 失败→raw
    
    # 情况5：2024 版总图工程编码（Z 前缀，自定义规则）
    #   【F3】非 9 位纯数字国标码；归一化键 = 'Z' + 后续大写字符；version 由 compute_match_key 强制 2024
    #   注：ZXXX 的精确结构/长度需对照 GB/T 50500-2024 附录确认，此处以"Z+后续字符"为稳定键
    elif code.upper().startswith('Z'):
        norm = 'Z' + code[1:].strip().upper()
        return norm, norm

    # 情况6：其他（自定义编码、含字母等）→ 原样返回，不匹配编码规则
    else:
        return code, code
```

> **关键说明**：
> - `item_code` 存规范化后的完整值（9位/12位/修正后的9位/Z键），`item_code_raw` 存单元格原始字符串，二者分离确保溯源审计
> - `match_key` 计算时统一用 `code_9`，且 **code 分支显式带入 `item_code_version` 维度**（`code:{ver}:{code_9}`），杜绝 2013/2024 跨版本同码误聚合（**F1**）
> - **11位编码处理**：识别为11位纯数字且首位≠0时，补前导0恢复为12位，截取前9位匹配（`10101001001` → `010101001001` → 匹配键 `code:unknown:010101001`）
> - **10位异常（F2 裁决）**：`0302280006`→`030228006`、`0304130010`→`030413010` 已知映射直接修正入库；其余未知 10 位原值入库 + warning，退化为 raw 匹配
> - **Z 前缀（F3）**：2024 版总图工程编码，强制 `version=2024` 走 `code:2024:Z<键>` 分支，不再退化为 raw 名称聚合
> - `parse_gb_code(code)` 返回 `(code_9, code_full)`，`code_9` 用于匹配，`code_full` 写入 `item_code`；原始值见 `item_code_raw`

`compute=True, store=True`，依赖 `material_dict_id / std_name / std_spec / item_code / item_name / item_feature / unit_std`，任一变化即重算。

> **【v6.5 澄清 · 身份 vs 键（P0-2 修正）】** `match_key` 是**行级候选归类键**——按该行「当前已填字段」生成，会随人工标准化升级而从 `raw:` → `std:` → `dict:`。它**不该被直接当作跨行聚合（join）键**：同一物理物料的 A 行（已标准化→`std:`）与 B 行（未标准化→`code:`/`raw:`）会因键型不同而**分裂成多条历史价**，而非一条可解释条目。
>
> **新增跨行聚合身份 `aggregate_id`**（计算字段，与 `match_key` 同依赖、同触发重算）：
> ```
> aggregate_id = f"dict:{material_dict_id.id}"   if material_dict_id else match_key
> ```
> 一旦某行挂上 `material_dict_id`，它本身及其所有同类（无论各自 `match_key` 是 `std/code/raw`）都并入同一 `dict:` 族。**M3 单价分析、M4 成本库迁移一律以 `aggregate_id` 聚合**，仅用 `match_key_source` 做口径解释——确保同一物料不因标注状态不同而分裂。

**③ `unit_std` 单位归一化 —— 跨工程聚合的前置条件（v2 遗漏）**

同一根电缆，A 工程写 `m`、B 写 `米`、C 写 `米(m)` —— 按原始 `unit` 聚合会被拆成三组，历史单价统计直接失效。

| 标准值 | 接受的写法 |
|---|---|
| `m` | 米 / m / M / 米(m) / 延米 / 延长米 |
| `kg` | 千克 / kg / KG / 公斤 |
| `t` | 吨 / t / T |
| `㎡` | 平方米 / m2 / m² / 平米 |
| `m³` | 立方米 / m3 / m³ / 立方 |
| `台`/`套`/`个`/`组`/`块`/`根`/`处` | 同义与全半角变体 |

规则：归一化前先去空白、全角转半角、转小写；命中映射则写入 `unit_std`；**未命中则原样小写存入并打 warning**（提示补映射）。**`unit` 原始值始终保留**，不覆盖。

> **职责边界**：`aliases.py`（表头列名）／`unit_normalize.py`（计量单位）／`material_dict.synonyms`（物料业务同义词）—— **三个字典分文件存放，互不混淆**。

### 4.8 `zaojia.audit.log`（不可变审计日志）【v3 新增】

| 字段 | 类型 | 说明 |
|---|---|---|
| `model` | Char(128) | 被操作模型（`zaojia.boq.item` 等） |
| `res_id` | Integer | 记录 ID |
| `action` | Selection | `create` / `write` / `soft_delete` / `restore` / `import` / `export` |
| `field_name` | Char(128) | 变更字段名（write 时逐字段记） |

| `user_id` | M2O → res.users | 操作人 |
| `timestamp` | Datetime，默认 now | 时间 |
| `batch_id` | M2O → import.batch | 关联批次（可空） |
| `reason` | Text | 人工填写的变更原因 |

**append-only 的三重保障**

| 层 | 做法 |
|---|---|
| 模型层 | 覆写 `write()` / `unlink()` / `create()` 之外的写路径 **直接抛 `UserError`**（`create` 保留给服务层内部调用，但**不对任何用户组开放 create 权限**） |
| 权限层 | `ir.model.access.csv`：所有组 `read` 1、`write` 0、`create` 0、`unlink` 0 |
| 视图层 | 仅 tree（只读）+ form（只读），**无 Create / Edit / Delete 按钮** |

**写入触发点（M1 必须接通）**

1. `boq_item.write()` 覆写：逐字段比对，**仅对实际变化的字段**写日志（避免日志爆炸）；B 类字段变化额外要求填 `reason`；
2. `import_batch` 的 导入 / 软删除 / 还原：服务层显式写；
3. 导出动作：M2 接通。

**B 类字段改 `reason` 的强制机制【v3.2】**：原生 form 保存走 `write()` 不会自动弹 `reason`，"要求填原因"不能只是一句空话。实现：① B 类字段在表单设为 `readonly`，**仅通过专用"修改标注"向导**修改，向导强制填 `reason` 才调 `write`；② `boq_item.write()` 覆写中若检测到 B 类字段变化而无关联 `audit_log` 记录，则拒绝并提示走专用向导——把"要求"变成机制强制。

**防篡改边界（诚实声明）【v3.2】**：三重保障防的是**应用层**篡改，**不防直连数据库改表**。对单人本地工具，辅以「数据库角色仅服务账号有写权限、日常账号无 `audit_log` 写权限」即可。若需更强保证，可后续引入**哈希链**（每条日志含前一条哈希）使事后能检测篡改——MVP 不实现，列入 P2。

### 4.9 数据分层与分层 Upsert（v3 推翻 v2 的 delete+insert）【P0】

**v2 的致命缺陷**

> 「同 `file_hash` 先删旧批次全部 boq_item 再写」—— 若用户已手工标准化该批次 300 行，重导一次，这 300 行人工资产**被级联删除且不可恢复**，界面只提示"已覆盖"。

**分层定义（写进代码常量，不是注释）**

| 类别 | 字段集合 | 重导时 |
|---|---|---|
| **A 类 · 可重建** | `item_code / item_name / item_feature / unit / unit_std / ordinal / sub_division / sequence / quantity* / unit_rate* / total* / provisional_sum* / classification / extra / source_path` | **允许覆盖更新** |
| **B 类 · 不可重建** | `std_name / std_spec / material_dict_id / anomaly_flag / anomaly_reason / data_source_type / 备注` | **禁止删除、禁止静默覆盖** |
| **C 类 · 系统** | `import_batch_id / file_hash / active / create_date / write_date` | 由批次管理 |

**Upsert 流程（M1 实现入库函数 `upsert_rows(batch, parsed_rows)`）**

| 步骤 | 规则 |
|---|---|
| 1. 匹配 | 按 `(import_batch_id, sequence)` 查已存在行；未命中再按 `(item_code_norm, item_name_norm, unit_std)` 匹配（应对原文件行序调整） |
| 2. A 类 | 命中 → `write` A 类字段；未命中 → `create`（此时 B 类字段按导入/默认规则写入） |
| 3. B 类 | **已有值则原样保留**；仅当"新建行"或"该字段为空"时才写入 |
| 4. 孤儿行 | 原批次有、新导入没有的行 → **不自动删**，标记 `orphaned=True`，进待确认列表（M2 界面决定保留/软删除/转存） |
| 4b. **孤儿行 B 类回灌【v6.5 新增 · P0-3 修正】** | 孤儿行常因「编码纠正 / 行序调整」导致 `(import_batch_id, sequence)` 与候选键都失配、被新建行取代，而孤儿行恰好带着人工 B 类标注（std_name/std_spec/material_dict_id/anomaly_*/data_source_type）。仅"保留不删"满足不了"可用"——标注会被埋进回收站、活数据拿不到。**规则**：生成孤儿行时，若孤儿行与某新建行经 `material_dict_id` 命中、或 rapidfuzz 高置信（≥0.98 且无歧义）判定为同一物料，则把孤儿行的 B 类字段**回灌到新建行**（新建行对应字段为空时才写入；已有值不覆盖），回灌动作**走专用标注向导 + 填 reason + 写 audit_log**，新建行 `preserved_manual` 计数 +1。这样重导既"不带走人脑产出"，又"让活数据拿得到标注" |
| 5. 返回 | `{created, updated, orphaned, preserved_manual}` 四项计数，**导入结果页必须全部展示**（计算方式见 M2 §3.4 预览计数逻辑） |
| 6. 审计 | 对 B 类字段的任何变更写 `audit_log`；对 A 类字段的批量更新**只写一条汇总日志**（避免日志爆炸） |

> **一句话**：**重导只能增加或修正"从 Excel 来的东西"，绝不能带走"人脑产出的东西"。**

**状态字段语义（防实现歧义）【v3.2 厘清】**：三类布尔状态必须分清——
- `active`：**软删除唯一判据**。`False` 即逻辑删除，列表默认过滤。
- `orphaned`：**仅由重导产生**（原批次有、新导入无的行）。非独立状态，是 `active=False` + `orphaned=True` 的待确认行，统一进回收站/待确认。孤儿行**不得**被当作"已删除的人工资产"误处理。
- `anomaly_flag`：表达**数据质量**（warning/error），与删除状态**正交**——异常行仍 `active=True`、正常参与查询与统计（空单价等被排除项除外）。
> 校验和（§4.10）只数 `active=True` 的行；孤儿行 `active=False`，不计入。

### 4.10 批次校验和【v3 新增】

入库完成后固化三项，存 `import_batch`（字段见 §4.2）：

| 校验项 | 计算 |
|---|---|
| `checksum_count` | 本批次 `active=True` 的 boq_item 行数 |
| `checksum_total` | `sum(total_num)`，`Decimal` 累加后取 2 位，再转 float 存 |
| `checksum_hash` | 按 `sequence` 升序拼接 `item_code|item_name|quantity|unit_rate|total`，UTF-8 编码后 SHA256 |

**导入完成时自动比对**（结果页展示）：

- `checksum_total` vs **Excel 合计行的合价** → 差值 ≤ 0.01 元或 ≤ 0.1% 视为一致，否则**高亮警示**（审计最常用的一条）；
- 提供「**重新校验本批次**」按钮：重算三项与存值比对，列出差异行 —— 检测数据漂移/误改的最快手段。

## 5. 模型关系

```
res.users ──< import.batch ──< boq.item >── M2O ──> material.dict
     │                            │
     │                       parent_id(self 层级)
     └──< audit.log (独立，不与其他模型建外键约束) ── 记录上述模型的变更
material.dict ── parent_id(self 三级树: l1→l2→l3)
```

- 一个批次含多行 boq_item；一行 boq_item 至多挂一个 material.dict；
- boq_item 自身 `parent_id` 表达「分部 → 清单项」层级；
- material.dict 自身 `parent_id` 表达「大类 → 系列 → 规格集合」三级；
- `audit.log` **不建外键**（`model` + `res_id` 软引用）：原因是即使原记录被物理删除，日志仍要留存，外键会连带删掉证据。

> **【v3 修正】删除行为**：~~删除批次 → 级联删除其 boq_item~~。改为 **软删除**（`active=False`）→ 其 boq_item **一并软删除**（可整体还原）；**物理删除**仅在硬删除闸门（二次确认 + 输入批次名 + 自动导出 CSV 快照到归档目录）后执行。理由见 §4.9。

### 5.1 外键删除策略（FK 审查）【v3.4 新增 · 中等风险项补强】

**问题背景（中等风险项）**：设计稿的删除语义是「软标记」（active=False / orphaned=True），但骨架模型曾用 `ondelete="cascade"`，二者冲突——cascade 会**物理连带删除**被引用行，绕过软删除闸门、且破坏审计溯源。必须全模块统一为「软标记优先、禁用 cascade」。

**外键删除行为表**：

| 外键字段 | 指向 | 删除策略 | 理由 |
|---|---|---|---|
| `boq_item.import_batch_id` | import.batch | `ondelete='restrict'`（**v3.8 修正**） | 见下方冲突说明：本字段 required，Odoo 19 不允许 required M2O 用 `set null`，只能 `restrict`/`cascade`。选 `restrict`：批次物理删除时若有明细行即被 **DB 拒绝**（等效禁 cascade、明细不随批次丢失）；批次的「删除」统一走软删 `active=False`，明细自然保留 |
| `boq_item.material_dict_id` | material.dict | `ondelete='set null'` | 字典项被改删时，明细行**保留**标准化结果，仅失联字典指针，B 类字段值本身不丢 |
| `boq_item.parent_id` | 自身（层级） | `ondelete='set null'` | 父项被删时子项降级为顶层，不级联删除子项 |
| `audit.log` | 任何模型 | **不建外键**（软引用 `model`+`res_id`） | 原记录物理删除后日志仍须留存，外键会连带删证据（见 §5） |

**铁律**：全模块 **禁止 `ondelete="cascade"`**；所有删除走软标记（`active=False` / `orphaned=True`）+ 物理删除闸门（二次确认 + CSV 快照）。`material_dict_id` / `parent_id` 等**非必填**外键用 `set null` 而非 `restrict`，确保引用方失效时数据不丢、可审计还原。

> **v3.8 冲突修正（M1.1 实测）**：`import_batch_id` 是 **required**（§4.1 表 ✅），而 Odoo 19 启动校验强制「required M2O 的 `ondelete` 只能 `restrict`/`cascade`，不允许 `set null`」（`ValueError: m2o field ... required but declares ondelete 'set null'`）。故 v3 铁律中「`import_batch_id` 用 set null」**无法落地**，改为 `restrict`：物理删批次带明细 → DB 拒绝（硬保护，比 set null 更安全）；业务上批次失效统一走软删，不触碰明细行。实现见 `boq_item.py` 注释。

## 8. 导入解析服务 `import_service.py`

**定位**：纯解析，**不直接写库**（写库由 M2 向导在用户确认后调用）。

**【v6.6 智能体就绪】** `import_service` 是 **Service 层**成员（架构 §19），其 `preview()` / `commit()` 方法**只接受文件引用（`file_id`=批次 `biz_id` / `file_path`=受控归档路径 `archive_path` / `file_hash`）、只返回结构化 `ParsedResult` 信封——**不依赖 Odoo 浏览器上传控件**。这意味着未来智能体持 `file_hash` 或 `archive_path` 即可触发导入，而非模拟页面上传（§8.6 时序的"归档→Upsert→校验和"由 `commit()` 内部统一编排）。

### 8.0 只读导入与安全前置校验【v3 新增 · P0】

这是**整个模块最容易出不可逆事故的地方**：openpyxl 默认以可写方式打开，且工作簿可 `save()`，一处误写就会覆写用户**不可重建的原始 Excel**。

| # | 规则 | 实现 |
|---|---|---|
| 1 | **只读打开** | `load_workbook(path, read_only=True, data_only=True)` —— 两个参数都必填 |
| 2 | **禁止保存** | 模块内**不持有可写工作簿**；代码审查红线：全文不得出现 `wb.save(` / `workbook.save(` |
| 3 | **格式白名单** | 仅 `.xlsx`；`.xlsm` / `.xlsb`（含宏）**直接拒收**并提示"请另存为 .xlsx"；`.xls` 提示转换 |
| 4 | **规模上限** | 单文件 ≤ **50MB**、单 sheet ≤ **20 万行**、列数 ≤ 200；超限拒绝并说明（防 zip bomb / 内存耗尽） |
| 5 | **外部链接检测** | 发现 `externalLink` 部件 → 标 warning（数值可能是缓存值，非实时） |
| 6 | **源文件指纹** | 打开前算一次 `file_hash`；**关闭后再算一次并比对** —— 不一致说明解析过程中文件被改动，直接报错中止 |
| 7 | **不移动不改名** | 解析与归档全程**只读源文件**，绝不 rename/move/delete |

> **`data_only=True` 的副作用——不能放松警惕**：公式单元格取 Excel 上次保存的缓存值，若文件从未被 Excel 打开并保存过则为 `None`。**造价软件导出的 xlsx 常在公式缓存为空时只留公式本身**，单价/合价等关键数值列可能整列为 `None`。**【v3.2 强化】** 解析完成后，若 `unit_rate`/`total` 等关键数值列**整列为空且文件含公式**，必须**明确报错或强告警并阻断入库**，不得仅"预览提示"——否则会静默导入一批全部无单价的垃圾数据。

**校验通过后的顺序（不可调换）**：

```
只读打开 → 解析（不写库）→ 用户预览确认 →【先归档复制】→【再写库】→ 固化校验和
                                              ↑ 归档失败 → 整批中止，一行不写
```

```
ParsedResult {
  rows:      [ {field: value, ...}, ...]           # 待入库行
  skipped:   [ {row_no, reason} ]                  # 汇总/合计行
  anomalies: [ {row_no, field, reason, level} ]    # 警告/错误
  header_map:{col_index: canonical_field}
  file_hash: str
  sheet_name: str
}
```

### 8.1 流水线（六步）

1. **定位 sheet**：优先匹配名称含 `分部分项`/`清单与计价` 的 sheet；否则取**首个能识别出 `项目名称` 表头**的 sheet；都失败 → 报错终止。**该 sheet 名称必须记入每个解析行的 `source_sheet` 字段**（多 Sheet 清单需能区分，见 §4.1 `source_sheet`）——这是单元格级溯源的 Sheet 维度，**v3.1 新增**。
2. **合并单元格填充**：`read_only` 模式的 Worksheet **无 `merged_cells` 属性**（M0 实测），合并结构须用**普通模式** `load_workbook(path)`（不 data_only）另读一次 `merged_cells.ranges`；数据行解析仍严格用 `read_only=True, data_only=True`。把左上角值填到区域内**所有**单元格（否则工程名称/分部只在第一行有值，其余为 `None`）。
3. **表头识别**：逐行扫描前 10 行，取**命中规范字段最多**的一行作表头（应对标题行/多行表头）。
4. **逐行解析**：见 8.2 汇总行、8.3 数值归一、8.4 异常规则。
5. **file_hash**：对文件**二进制内容**算 SHA256（比"路径+大小+时间"更可靠，文件改名/移动不影响幂等）。
6. **返回**：不写库，交调用方。

### 8.2 汇总行识别（双重判定，避免误杀）

命中 **名称模式** 且 **量价为空** → 判为汇总行，进 `skipped`：

- 名称模式：`^(合计|小计|总计|合　计|.*工程合计|.*分部合计|.*小计.*)$`
- 量价为空：`quantity` 与 `unit_rate` **同时**为空/0

> 只凭名称会误杀名字里带"合计"的真实清单项；加上"量价为空"可基本杜绝误判。

### 8.3 数值归一化

| 输入 | 处理 | 结果 |
|---|---|---|
| `"1,234.50 元"` | 去逗号/空格/货币符/全角数字 → `Decimal("1234.50")` | `quantity="1,234.50"`（原始）、`quantity_num=1234.50` |
| `1234.5`（数值型） | 直接转 `Decimal(str(v))` | 文本列存 `"1234.5"` |
| `""` / `None` / `"-"` | 视为空 | 数值列留空（nullable），**不填 0** |
| `"1.2e3"` / 含字母 | 尝试解析，失败 → 标「错误-数值不可解析」，文本保留原样 |
| 负数工程量 | 标「错误-工程量为负」 | 仍入库，交由人工判断 |

### 8.4 异常规则表（M1 打标，M3 展示）

| 级别 | 场景 | 处理 |
|---|---|---|
| **错误** | `item_name` 为空 | **不进 rows**，进 errors（无名称的行无意义） |
| **错误** | 工程量 ≤ 0 或不可解析 | 入库 + `anomaly_flag=error` |
| **错误** | 单价不可解析（非空的脏值） | 入库 + error |
| **警告** | 单价为空 | 入库 + warning，**统计时排除**（符合"约12%无单价"现实） |
| **警告** | **合价 ≠ 工程量 × 单价**（容差：绝对值 0.01 或相对 0.1%） | 入库 + warning —— 审计最常用的一条 |
| **警告** | 工程量 > 1e9 或 单价 > 1e7（异常量级） | 入库 + warning |
| **警告** | `item_code` 长度 ≠ 12 或含非数字 | 入库 + warning（老清单常见，不阻断） |
| **警告** | 含控制字符/乱码特征（连续 `?`、替换符 `\ufffd`） | 入库 + warning |
| **警告** | 同批次内同一 `item_code` 出现**多种单位** | 入库 + warning（提示口径不一致） |

> **单批失败隔离**：单行解析异常**绝不中断整批**（用户明确的铁律），只打标，继续跑完。

### 8.5 原始文件归档 `archive_service.py`【v3 新增 · P0】

**为什么不用 Odoo 的 `ir.attachment`**：附件进 filestore 后由 Odoo 托管，会受附件真空清理、模块卸载、数据库重建影响。**造价原始凭证需要"我自己能牢牢看住的目录"——Odoo 崩了、重装了、换版本了，文件还得在。**

| 项 | 规则 |
|---|---|
| 归档根目录 | 配置项 `zaojia.archive_root`（默认 `<Odoo 数据目录>/zaojia_archive`），**M0 阶段规划，装完环境即建** |
| 路径规则 | `<root>/YYYY/MM/<file_hash[:2]>/<原文件名>`；同名文件加 `_<file_hash[:8]>` 后缀，**不覆盖已有归档** |
| 元信息 | 同目录写 `<原文件名>.meta.json`：`{原路径, 大小, sha256, 导入时间, 批次ID, 操作人}` |
| 时机 | **先可重入地成功复制归档（幂等，不覆盖已有同名归档），再写库**；任一步失败 → 整批中止。**文件系统复制与 PG 事务不是同一事务**——若写库失败回滚，已复制的归档文件**无害残留**（下次同 `file_hash` 重导复用，不重复复制），不留孤儿（v3.2 纠正"同一事务"措辞） |
| 权限 | 归档目录对日常账号设**只读**（去掉写/删），只能追加（Windows 用 icacls 配置，写入脚本随 M0 一起交付） |
| **静态加密【v3.1】** | 原始文件属商业敏感数据；归档根目录应置于 **BitLocker / EFS 加密卷**，或至少 NTFS ACL 限定仅 zaojia 服务账号可读。**v3 只要求"只读"，未要求加密**——只读防误改但不防有读权限者拷走。与 `架构设计.md` 4.4「静态机密性」一致 |
| **⚠️ 加密密钥必须异地备份【v3.2】** | **EFS 证书 / 加密盘恢复密钥必须与归档文件分开异地备份**。密钥一旦丢失（重装系统/证书损坏），加密后的真相源**永久无法打开**，等于制造新的"不可重建"风险，与 4.1 第一原则相悖。加密把"可用性"押在密钥管理上，M0 规划须一并交付密钥备份方案 |
| 完整性校验 | 提供 `verify_archive()`：遍历归档目录重算 SHA256，与 `import_batch.file_hash` 逐项比对，返回不一致清单 |
| 数据库 | `import_batch.archive_path` 存**相对路径**（便于整体搬迁归档目录） |

### 8.6 入库调用时序（M1 实现，M2 向导调用）

```
1. parse(file)                    → ParsedResult        # 只读解析，不写库
2. 用户在预览页确认（M2 UI）
3. archive_service.archive(file)  → archive_path        # 失败 → 中止，一行不写
4. batch = import_batch.create({...})                   # 建批次
5. upsert_service.upsert_rows(batch, parsed.rows)       # §4.9 分层 Upsert
6. batch.write({checksum_count, checksum_total, checksum_hash})   # §4.10
7. audit_log.create(action='import', batch_id=batch.id, ...)
8. 返回 {created, updated, orphaned, preserved_manual}  # 结果页四项计数全展示
```

> 步骤 3 归档**幂等先行**（不在 PG 事务内），步骤 4–7 写库在**同一数据库事务**内；任一步失败整体回滚。**归档幂等机制**（同 `file_hash` 不重复复制）见 §8.5。

## 16. 智能体就绪：Service 层与稳定 ID（架构 §19 落地）【v6.6 新增】

M1 是数据层，本节的落地要点是把"核心能力从 UI 抽离"在骨架阶段就钉死，避免后期返工。

### 16.1 稳定业务 ID（`biz_id`）

| 模型 | 字段 | 生成 | 未来 API 语义 |
|---|---|---|---|

| `import.batch` | `biz_id` Char(36) unique index | 同上 | `batch_id` / `source_file_id` |

### 16.2 Service 层目录与边界

- 目录：`zaojia_boq/services/`（§2 已列），含 `import_service` / `upsert_service` / `archive_service` / `boq_query_service` / `batch_service` / `evidence_service`。

## 17. M1.1 落地实证：Odoo 19 API 偏差与实现对照【v3.8 新增 · 2026-09-03 M1.1 完成】

M1.1 骨架已落地并通过集成测试（13/13 PASS，`zaojia_boq` 模块可安装）。以下为**在 Odoo 19.0 源码与运行中实测核实**的 API 偏差，后续 M1.2–M1.6 直接引用，不再重蹈。

| # | 设计稿原假设 | Odoo 19 实测 | 影响与落地 |
|---|---|---|---|
| 1 | `fields.Char(size=n)` 限制长度 | `size` 参数**已移除**（仅存 deprecated 类属性 `size=None`） | 列定义不体现长度（PG 无上限 varchar）。`Char(n)` 仅作**业务约定**；强约束处用业务校验或 unique index（如 `biz_id`=36）。字段文件头部注记 |
| 2 | `widget="month"`（月份选择） | **不存在**；month 精度用 Date + `options="{'max_precision':'months'}"`（`web/static/src/views/fields/datetime/datetime_field.js` 实测 options `min_precision`/`max_precision`） | `price_period` 仍为 `fields.Date` 存当月 1 日（§4.3① 不变）；M1 暂缓 month 控件，后续用 options |
| 3 | 复合索引用 `post_init_hook`+`migrate`（v6.2） | **声明式索引**：`models.Index('(a, b)')` / `models.UniqueIndex(...)`（`odoo/models.py` 重导出 `odoo.orm.table_objects`），模型类属性名须 `_` 开头；安装/升级双路径 ORM 自动维护 | v6.2 方案作废。`boq_item` 四条复合索引 + `biz_id` UniqueIndex、`import_batch` file_hash/biz_id、`material_dict` biz_id、`audit_log` (model,res_id) 全部声明式落地 |
| 4 | `_parent_store=True` 自动建 `parent_path` | **须显式声明** `parent_path = fields.Char(index=True)`（否则 `KeyError 'parent_path'`），且不接受 `unaccent` 参数 | `material_dict` 已显式声明（§4.6 不变，仍启用） |
| 5 | `import_batch_id`（required M2O）`ondelete='set null'` | required M2O 的 ondelete **只允许 `restrict`/`cascade`**，`set null` 启动即 `ValueError` | 改 `restrict`（DB 级拒绝物理删有明细的批次），业务删走软删。详见 §5.1 v3.8 修正 |
| 6 | `__manifest__.py` 可含 docstring/变量 | 经 `ast.literal_eval` 读取，**只允许注释 + dict 字面量**；docstring/代码 → 模块被忽略（`invalid module names, ignored`） | manifest 文件纯注释+dict |
| 7 | manifest `version` 任意 | **首段须匹配 Odoo 大版本**（`19.0.x.y.z`），否则判 `incompatible` 拒装 | 模块版本 `19.0.1.0.x` |
| 8 | search 视图 `<group expand="0" string="...">` | `<group>` 容器**只允许裸标签**，不允许 `string`/`expand` 等属性（RELAXNG 校验报错） | search 视图分组用裸 `<group>` |
| 9 | CSV 数据文件 UTF-8 无 BOM | Windows 写出 CSV 首列常带 `\ufeff` → `Invalid field name '\ufeffid'` | 导入/生成 CSV 须剥 BOM |
| 10 | 测试发现机制 | 测试须 `tests/__init__.py` 显式 `from . import test_xxx`；`-u` 对 `uninstalled` 模块不生效，首次须 `-i` | `zaojia_boq/tests/` 已显式 import；AGENTS.md 命令含 `--test-tags /zaojia_boq` |

**模块内 addon 引用**：测试/脚本 import 本模块服务须用 `odoo.addons.zaojia_boq.services.xxx` 命名空间（顶层 `zaojia_boq` 不在 `sys.path`）。
