## 一、定位与目标

### 1.1 一句话定位

M3 的目标用户是**正在对清单做价格决策的造价工程师**——不是做日常数据录入的人，而是需要"这个清单项历史做过多少钱、这次报的价合不合理"的人。

### 1.2 核心业务问题（对应产品文档场景 2）

> **"同编码/标准化项横向对比，偏离区间标红"**——这是审计场景的硬需求，不是锦上添花。

M3 要回答的四个问题：

| 问题 | 数据来源 | 输出 |
|---|---|---|
| 这个清单项历史做过多少钱？ | `boq_item` 按 `match_key` 聚合，默认域 `data_source_type=completed` | 样本数 / 均价 / 区间 / 异常数 |
| 这次报的价偏不偏？ | 当前清单 `unit_rate_num` vs 历史区间 | 红色高亮 + 偏离百分比 |
| 这条人工标注还靠谱吗？ | `audit_log` + `B 类字段` 记录 | 变更轨迹可追溯 |
| 相似的历史项是哪些？ | `material.dict` + rapidfuzz 召回 | Top-N 候选建议 |

### 1.3 本节范围

**进 M3**：单价分析页（KPI 卡片 + 透视表 + 异常高亮）、快速匹配向导（rapidfuzz）、批量标注确认、成本库评估说明。

**不进 M3**：cost.catalog 独立表（仅评估）、LanceDB 向量语义检索（M4）、人材机分析（P3）、**项目特征描述标准化（见 §十四 占位草案，登记但未排期）**。

## 三、单价分析页

### 3.1 页面结构

**顶部 KPI 卡片**（4 张，M1.5 §6.6 已定义样式，M3 直接复用）：

| 卡片 | 指标 | 数据来源 |
|---|---|---|
| 样本数 | 符合筛选条件的 completed 行总数 | 调用 M1 定义的统计方法（默认域已含 `data_source_type=completed`） |
| 均价 | 算术平均（排除 unit_rate_num 为空） | 同上，**不重复定义 domain** |
| 区间 | 最低 / 最高 | 同上 |
| 异常数 | 偏离均值 ±阈值 的行数 | 仅展示，**不写回 anomaly_flag**（见 §3.4） |

**主内容区**（左右布局）：

- **左侧**：搜索 / 筛选条件复现（复用 M2 搜索视图的 filter/groupby 定义，见 §4）
- **右侧**：透视表（pivot）+ 异常行列表（单列视图，红色高亮）

**底部**：统计口径说明（样本数构成、匹配来源分布）

### 3.2 KPI 卡片实现

**复用 M1.5 §6.6 自定义 OWL 组件**，M3 不重新定义样式：

- QWeb 模板调用 `<kpi-card>` 组件，传 `title` / `value` / `unit` / `color` 参数
- 数据源：`analysis_service.get_kpis(domain)` 服务层方法，走 Odoo 原生聚合（`read_group`），**前端不二次计算**
- 默认域：`[('data_source_type', '=', 'completed'), ('unit_rate_num', '!=', False)]`——**排除 pending_review / controlled_price / bid_price / info_price**

> **⚠️ 为什么默认域必须是 completed？**
> 继承 M1 §4.7 的统计方法（默认域已含 `data_source_type=completed`），**不在此重复定义**。M2 的 `data_source_type` filter 为多性质查询服务，M3 的均价卡片只展示"已完工程"口径——这是防污染原则的直接落地。

> **【v6.6 智能体就绪】** KPI 计算与区间判定全部经由 Service 层（`price_service`，见 §二目录），Odoo 页面仅是调用方之一；同一方法以**结构化 JSON** 返回（`success/data/total/warnings/trace_id`，错误统一机器可识别错误码，见 架构设计.md §19），供未来 `POST /api/v1/price/search`、`POST /api/v1/price/analyze` 直接复用——「前端不二次计算」的原则同时保证了能力可编程调用。

### 3.3 透视表（pivot）

**视图类型**：`pivot`（Odoo 原生），**非 chart**（M3 不做趋势图，P3 再做）

**分组维度**（用户可拖拽切换）：

| 维度 | 含义 |
|---|---|
| aggregate_id | 按跨行聚合身份聚合（核心，见 M1 §4.7；确保同一物料的不同标注状态行并为一族，避免历史价分裂成重复条目） |
| match_key_source | 编码匹配 / 标准化 / 原始名称（统计口径可解释） |
| province | 按省份分组 |
| price_period | 按月分组（`price_period` 存当月 1 日，可 month 分组） |

**度量**：

| 度量 | 操作 |
|---|---|
| unit_rate_num | avg / min / max / count |
| quantity_num | sum（总量） |
| amount_num | sum（总价） |

**异常标记**：当 avg 偏离历史均值超过阈值时，该格子背景色为 `rgba(var(--zj-danger), 0.08)`，并加 ⚠️ 图标。

### 3.4 异常高亮逻辑

**偏离判定规则**（见 `data/analysis_rule_data.xml`）：

| 规则 | 默认值 | 说明 |
|---|---|---|
| 阈值 | ±30% | 偏离均值 30% 以内视为正常 |
| 样本下限 | 3 | 样本数 < 3 时不判异常（统计不可靠） |
| 异常标记 | 仅展示，不写回 | **透视表红色高亮是计算结果，不写回 boq_item.anomaly_flag**（见下方说明） |

**偏离百分比计算**：

```python
deviation_pct = (current_price - historical_avg) / historical_avg * 100
is_anomaly = abs(deviation_pct) > threshold and sample_count >= min_sample
```

**展示**：
- 透视表格子：红底 + 图标（仅视觉高亮，不改数据）
- 异常行列表：独立 tab，显示 deviation_pct 字段（数值列，右对齐）

> **保留机制**：M3 的异常判定**只读展示**，不写回 `boq_item.anomaly_flag`。理由：原始单价由人决定，工具只做提示，不因"算法判定"自动改数据（与架构 §4 安全原则一致）。
>
> **与批量确认的边界**：
> - **透视表高亮**：算法计算结果，只读展示，不改数据
> - **批量确认**：用户主动操作，通过专用向导修改 `anomaly_flag`（B 类字段），强制填 reason，写 audit_log

M3 的单价分析页**复用 M2 §4 的搜索视图定义**，但在透视表上下文下增加两个能力：

### 4.1 匹配来源分布（新增 chip）

**filter 选项**（在 M2 §4.1 基础上增加）：

| filter | 名称 | 类型 | 用途 |
|---|---|---|---|
| `match_key_source` | 匹配来源 | 单选 chip | 按编码/标准化/原始名称分别看均价 |

**统计口径可解释**（架构 §7.5 落地价值）：

### 4.2 偏差阈值可调（新增 slider）

**UI 控件**：输入框 + slider（范围 10%–50%，步长 5%），默认 30%。

**作用**：调整异常判定的敏感度，高敏感（10%）适合严控项目，低敏感（50%）适合参考性查询。

> **⚠️ 阈值存储位置**：存在 `ir.config_parameter`（系统参数），**非 boq_item 字段**。理由：阈值是全局偏好，与单条数据无关；改阈值不影响历史数据。

## 五、快速匹配向导（rapidfuzz）【P1 · 架构 §十一】

### 5.1 定位与触发

**触发条件**：用户选中若干 `boq_item` 记录（`material_dict_id` 为空或 `anomaly_flag='warning'`），点「快速匹配」按钮。

**核心约束**（架构 §十一硬规则）：
> **仅候选建议，绝不自动改 `boq_item`；人工确认后回填 `std_name/std_spec/material_dict_id`，且写 `audit_log`。**

### 5.2 向导流程

```
选择行（可多选）
    ↓
调用 rapidfuzz 从 material.dict 召回 Top-5 候选
    ↓
展示候选列表（名称 / 规格 / 相似度分数 / 分类路径）
    ↓
用户逐项确认（单选 / 多选 / 忽略）
    ↓
确认后批量写入 std_name / std_spec / material_dict_id
    ↓
写 audit_log（B 类字段变更，required reason）
    ↓
结果摘要（N 行匹配成功 / M 行忽略）
```

### 5.3 召回逻辑

**输入**：`boq_item.item_name` + `boq_item.item_spec`（归一化后）

**候选来源**：`material.dict`（按 L1→L2→L3 路径加权打分）

**相似度算法**：`rapidfuzz.fuzz.ratio`（全字符匹配） + `partial_ratio`（子串匹配）

**打分规则**：

| 匹配位置 | 权重 |
|---|---|
| L3 规格精确匹配 | 1.0 |
| L2 系列匹配 | 0.8 |
| L1 大类匹配 | 0.5 |
| 名称相似度 > 90 | 0.3（加分项） |

**返回**：Top-5 候选，含 `dict_id` / `name` / `spec` / `score` / `category_path`

> **性能提示**：material.dict 是**小表**（预计 < 1000 行），M1 §4.6 已启用 `_parent_store`（须显式声明 `parent_path`），召回耗时 < 100ms，无性能风险。

### 5.4 回填与审计

**回填字段**：`std_name` / `std_spec` / `material_dict_id`（均为 B 类字段，见 M1 §4.9）

**审计要求**：
- 每次回填写 `audit_log`，`reason` 必填（向导强制输入）
- 日志条目格式：`"快速匹配确认：将 <item_name> 标准化到 <dict.name>，相似度 <score>"`
- 回填后重新计算 `match_key`（compute+store，自动触发）

### 5.5 边界情况

| 情况 | 处理 |
|---|---|
| 无候选（相似度均 < 60） | 提示"未找到匹配，请手动建立字典项" |
| 候选重复（同一 dict_id 出现多次） | 去重，只显示一条 |
| 部分确认、部分忽略 | 只写入确认的行，忽略的行保持原样 |
| 批量操作行数 > 50 | 二次确认，提示"本次将标准化 N 条记录" |

### 5.6 高置信自动链接（减负，不静默覆盖）【v6.5 新增 · P2-4 修正】

审查指出：三套匹配都「仅候选、人工确认才回填」，导致数千行人工标注**每行都等人工点**，而真正稀缺的是「人的标注时间」。在守住「不静默覆盖」底线的前提下，允许**高置信自动链接**：

| 条件 | 自动动作 | 审计 |
|---|---|---|
| 行的目标字段（`std_name`/`std_spec`/`material_dict_id`）**为空**，且匹配满足高置信判据之一 | 自动回填候选值到该**空字段**（**绝不覆盖已有值**） | 自动写 `audit_log`，`reason` 含 `auto_linked` 标记（如"高置信自动链接 rapidfuzz=0.99"），便于按审计记录批量复核/撤销 |
| 高置信判据 | ① 精确国标 9 位编码命中 `material.dict` 同款；或 ② rapidfuzz 相似度 **≥ 0.98 且无歧义**（Top-1 与 Top-2 分差 > 0.1） | — |

**底线不变**：B 类字段已有值**绝不自动覆盖**；自动链接只填空字段、必留审计、支持「按 `audit_log` 中 `auto_linked` 记录一键复查/撤销」。低置信（< 0.98 或存在歧义）仍走原有「仅候选、人工确认」流程。如此标注工时显著下降（架构 §4.15 指标：较全人工下降 ≥60%），又不牺牲可追溯与安全。

> **【v6.6 写操作元数据】** 匹配确认回填（§5.4）与高置信自动链接（本节）均属**写操作**：无论入口是 Odoo 向导还是未来 API，都必须携带 `operator / reason / trace_id` 并写入 `audit_log`（架构设计.md §19 读/写分离原则）。召回候选（`material_match_service.find_matches`）属读操作可直接调用；确认回填（`confirm_match`）必须走独立写接口并带审计元数据。召回结果以**结构化 JSON** 返回（含 `dict_id/name/spec/score/category_path`），供未来 `POST /api/v1/material/match` 复用。

## 六、批量操作增强

M3 在 M2 的基础上增加**分析上下文下的批量操作**：

### 6.1 异常行批量确认

**场景**：透视表异常高亮后，用户选中若干异常行，点「批量确认」——表示"我知道这些偏离了，但报价合理"。

**操作**：
1. 调用专用「异常标注」向导（B 类字段变更强制走向导，见 M1 §4.9）
2. 向导选择目标状态（warning / normal），**强制填写 reason**
3. 向导调用 `boq_item.write()`，`anomaly_flag` 从 `'error'` 改为目标值
4. 写 `audit_log`（B 类字段变更，reason 必填）
5. 刷新界面

> **⚠️ 为什么 anomaly_flag 改 warning 而不是删除？**
> 保留历史记录，审计可查看"这条曾经被判异常，后被人工确认"的轨迹。
>
> **⚠️ 为什么必须走专用向导？**
> `anomaly_flag` 是 B 类不可重建字段（M1 §4.9），原生 form 直接修改会绕过审计机制。专用向导强制填 reason，确保每条变更可追溯。

### 6.2 数据性质批量切换

**场景**：用户发现误选 `data_source_type`，需要批量修正。

**操作**：
1. 选中若干行，点「切换数据性质」
2. 选择目标性质（completed / pending_review / ...）
3. 若切换到 `completed`，**强制二次确认**："本批将计入历史均价，确认？"
4. 写 `audit_log`（B 类字段变更，reason 必填）

> **防污染闸门**：若目标性质为 `completed` 且原性质为 `pending_review`，需额外显示"此操作会影响历史均价统计"的警告。

## 七、成本库评估（架构 §7.4 · 风险9 方案B）

M3 不做独立 `cost.catalog` 表，但提供**评估说明与数据质量检查**，为 M4 决策提供依据。

### 7.1 评估维度

| 维度 | 检查项 | 达标线 | M4 迁移门槛 |
|---|---|---|---|
| 标准化覆盖率 | `material_dict_id` 非空的行数 / 总行数 | ≥ 70% | **≥ 80%**（M4 决策依据） |
| match_key 质量 | 优先级 1（dict）占比 / 优先级 4（raw）占比 | 优先级 1+2 ≥ 80% | 同左 |
| 数据性质分布 | completed / pending_review / ... 占比 | completed ≥ 60% | 同左 |
| 异常率 | `anomaly_flag='error'` 占比 | < 15% | **< 10%**（M4 决策依据） |

> **⚠️ 门槛差异说明**：M3 的评估仪表盘使用较宽松的门槛（70%/15%）作为**数据质量参考**；M4 的 cost.catalog 迁移门槛更严格（80%/10%）。两者不一致是故意的——M3 帮助用户看到"数据质量现状"，M4 决策者看到"是否达到迁移门槛"。若用户认为应统一，可在实施时调整。

### 7.2 评估输出

**单价分析页底部新增「数据质量仪表盘」**：

- 四个进度环（标准化覆盖率 / match_key 质量 / 数据性质分布 / 异常率）
- 每项显示达标状态（✅ / ⚠️ / ❌）
- 未达标项显示具体数字与建议

**决策建议**：

| 达标情况 | 建议 |
|---|---|
| 全部 ✅ | 可评估独立 cost.catalog 表（M4 决策） |
| 部分 ⚠️ | 先补标准化（run rapidfuzz 匹配向导）再评估 |
| 严重 ❌ | 暂缓，先完成数据治理 |

### 7.3 cost.catalog 评估逻辑（M4 用）

若 M4 决定建独立 `cost.catalog` 表，M3 的评估结果直接作为**迁移门槛**：
- 只有标准化覆盖率 ≥ 80% 且异常率 < 10% 时，才建议启动 cost.catalog 迁移

## 十四、特征描述标准化（占位草案 · 未排期）

> 待 M1 骨架落地、积累到真实数据样本后，再细化解析规则并评估是否排期。

### 14.1 问题背景与命名约定

清单表中的**项目特征描述**（`item_feature`）在国标体系（GB/T 50500）中是一段**自由文本**，
把规格、材质、连接方式、压力等级、安装部位等多维信息混排在同一列。例：

```
DN100 镀锌钢管 沟槽连接 1.6MPa 室内明敷
```

**命名约定（2026-09-02 确定，全项目统一）**：

| 项 | 结论 |
|---|---|
| 界面表头 | 统一用 **`项目特征描述`**（国标正式列名），**不再用"规格型号"** |
| 理由 | 该列内容远超规格型号范畴；称"规格型号"会误导使用者以为其中只含规格，进而按规格口径去做比价与匹配 |
| 导入向导 | 源表头"规格型号"仍作为 `item_feature` 的**别名**参与列识别，映射到 `item_feature`，**不单独建字段**（遵循 M1 §7 `aliases.py` 列别名机制） |
| 已同步位置 | `demo/style-lab/index.html` 检索结果表头、导入列映射表 |

### 14.2 要解决的问题与收益

| 收益 | 说明 | 受益模块 |
|---|---|---|
| `match_key` 更稳 | 现依赖 `std_name + std_spec + unit_std`，`std_spec` 是整段文本，同一条管子写法差一字即失配；拆分后按维度比对，容忍度提升 | M1 §4.7、M3 §5 |
| 单价可比性提升 | 当前按 `match_key` 聚合比价，可能混入不同规格（DN100 与 DN150 同码）；拆分后可按规格口径分组再比 | M3 §3 |
| 相似项召回更准 | 结构化字段比整段文本噪声小，embedding 拼接质量也更高 | M3 §5、M4 §5 |

**改名与标准化的关系**：改名只解决"叫错"，不解决"数据还是一团"。
真正的收益来自把这段文本**解析为结构化字段** —— 这才是本节登记的能力。

### 14.3 字段草案（未定稿）

> 均为**候选字段**。字段名、类型、是否落库，待真实样本验证后确定。**当前不建表、不加字段。**

| 候选字段 | 类型 | 含义 | 示例 |
|---|---|---|---|
| `feat_spec` | Char | 规格型号（公称直径 / 截面 / 容量等） | `DN100` |
| `feat_material` | Char | 材质 | `镀锌钢` |
| `feat_conn` | Char | 连接方式 | `沟槽` |
| `feat_pn` | Char | 压力等级 | `1.6MPa` |
| `feat_part` | Char | 安装部位 / 敷设方式 | `室内明敷` |
| `feat_rest` | Text | 未能解析的剩余文本（保证不丢信息） | — |
| `feat_confidence` | Float | 解析置信度（0–1），低值需人工复核 | `0.82` |
| `feat_version` | Char | 解析规则版本，用于追踪规则变更后的重解析 | `v1` |
| `feat_confirmed` | Boolean | **是否已人工确认** —— 决定该行 `feat_*` 的 A/B 类归属（见 §14.5 第 2 条） | `False` |

### 14.4 解析策略草案（三选一，未定）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 规则 / 正则 | 按专业（安装 `03` / 市政 `04` / 房建 `01`）分别写正则与词典 | 可解释、零成本、易审计 | 覆盖率依赖词典持续维护 |
| B 词典 + 模糊 | 由物料字典 `spec_whitelist` 驱动，rapidfuzz 匹配 | 复用 M1 既有资产 | 新词需人工补录 |
| C 大模型抽取 | 调 LLM 做结构化抽取 | 覆盖率高、泛化强 | 成本高、结果需复核兜底 |

**倾向**：先 A + B 组合（规则 + 字典），C 留作后续扩展。

**硬约束（无论选哪套）**：解析结果**一律为建议值**，人工确认后才回填；
禁止自动改写 `boq_item`，遵循 M1 §4.9 的 B 类字段约束。

### 14.5 与既有设计的约束关系

1. `item_feature` **保留原值不动**，解析结果只写入新的 `feat_*` 字段，原始文本始终可溯源；
2. `feat_*` 的**分层归属按「是否已人工确认」区分**，严格遵循 M1 §4.9 的分层原则
   （*"重导只能增加或修正从 Excel 来的东西，绝不能带走人脑产出的东西"*）：

   | 状态 | 归属 | 重导 / 规则升级时 |
   |---|---|---|
   | 机器解析的**建议值**（未确认） | **A 类 · 可重建** | 允许重算覆盖（源自 `item_feature`，本就可再生） |
   | **人工确认 / 修正后**的值 | **B 类 · 不可重建** | 禁止删除、禁止静默覆盖；修改须走专用向导 + `reason` 必填 + 写 `audit_log` |

   > **为什么不能整体划 B 类**：解析值是机器从 `item_feature` 算出来的，本质上"可再生"；
   > 若一律划 B 类，规则升级后无法批量重解析，反而把脏数据固化下来。
   > 真正需要保护的只有**人工确认过的那部分**。判据字段见 §14.3 的 `feat_confirmed`。
3. `match_key` 优先级**暂不变**（**M1 §4.7** 数据性质与同类项聚合键 / 架构 §7.5），
   待标准化覆盖率与准确率验证达标后，再评估是否引入为更高优先级的聚合键；
4. **不阻断导入**：解析失败或置信度低时字段留空，不影响入库与检索；
5. 导出时 `feat_*` 归入**标准化字段**组，与 `std_name` / `std_spec` 并列（对齐 M2 §6.1）；
6. **两个字段不要混淆**（实施时高频踩坑）：

   | 字段 | 界面列名 | 性质 | 分层 |
   |---|---|---|---|
   | `item_feature` | **项目特征描述** | 原始自由文本（一整段，未结构化） | A 类，从 Excel 导入 |
   | `std_spec` | **规格** | 人工标准化的规格（已结构化） | B 类，人工确认产出 |

   > M2 §4.3 列表视图默认 11 列中的「规格」列是 **`std_spec`**，**不是** `item_feature`；
