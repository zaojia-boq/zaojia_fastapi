## 一、定位与目标

### 1.1 一句话定位

M4 的目标是把"散落在 boq_item 里的历史单价"提炼成**独立、可复用、可语义检索的成本库**，并在此基础上提供**超越关键词匹配的语义检索能力**。

### 1.2 核心业务问题

M3 的评估仪表盘已回答"数据质量够不够建独立 cost.catalog 表"。M4 要解决的是：

| 问题 | 为什么需要 |
|---|---|
| cost.catalog 独立表：从 boq_item 聚合成"标准化历史价" | boq_item 是事务记录，不是价格基准；跨工程查询要 GROUP BY match_key，性能差且口径混乱 |
| LanceDB 语义检索：超出精确匹配的查找 | "电缆 YJV 4*16mm² 铜芯" 和 "YJV铜芯电力电缆 16平方" 是同一东西，字符串相似度不够时用 embedding 召回 |
| 迁移闸门：什么时候该建 cost.catalog | M3 的评估仪表盘给出量化门槛，M4 据此决策 |

### 1.3 本节范围

**进 M4**：cost.catalog 独立表设计、数据迁移策略、LanceDB 向量检索服务、语义匹配向导 UI、迁移闸门条件。

**不进 M4**：人材机分析（P3）、4D 排期（P3）、embedding 模型选型细节（留 P2 评估）。

## 三、cost_catalog 独立表设计

### 3.1 设计理由

> **【v6.5 重构 · 消除与 §4.1 矛盾（P1-1 修正）】** `cost.catalog` **不是「第二真相源」**，而是**派生自 `boq_item` 的只读预聚合缓存（物化视图等价物）**：它**不接收任何直接写**、只能由迁移/刷新从 PG 重算生成，可随时从 `boq_item` 重建。因此它不构成 架构 §4.1 所反对的「第二个不可重建真相源」——真相源始终是唯一且不可重建的原始 Excel。启用前提是规模假设被突破（见 架构 §4.14），否则 MVP 直接在 `boq_item` 上按需聚合即可（方案 A）。

> **【v6.6 智能体就绪】** cost.catalog 作为只读派生缓存，对外一律经 **Service 层**暴露（`price_service` / 查询服务），Odoo UI 与未来 `POST /api/v1/price/*` 共用同一套方法；LanceDB 向量检索封装（§5.4 `VectorSearchService`）同属独立 Service 层，不与 Odoo UI 绑定（架构设计.md §19）。对外标识使用 `biz_id` 稳定业务 ID（§3.2），不以 Odoo 自增 id 作为接口协议依据。

**为什么在规模突破时需要独立缓存（而非一直用 boq_item 聚合）？**

| 问题 | boq_item 现状 | cost_catalog 解决方式 |
|---|---|---|
| 口径混乱 | 一条 `aggregate_id` 对应多条记录（不同工程、不同时间） | 每条 `aggregate_id` 一条记录，取最近 completed |
| 查询慢（仅超大规模时） | 超 5000万行时 GROUP BY `aggregate_id` 实时聚合可能变慢 | 直接读单条记录，毫秒级 |
| 人工标注分散 | std_name/std_spec 可能只在一部分行上有值 | cost_catalog 是"已确认为标准的记录"，天然干净 |
| 可复用性差 | boq_item 与具体项目绑定 | cost_catalog 是跨项目通用基准，任何新项目可直接参考 |

### 3.2 数据模型

**`zaojia.cost.catalog`**

> **Odoo 19 实测（M1.1）**：`fields.Char` 已移除 `size` 参数。下表 `Char(n)` 的 `n` 仅为**业务长度约定**（列定义不体现长度，PG 为无上限 varchar）；需强约束处由业务校验/unique index 保证。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `match_key` | Char(256), unique | ✅ | 聚合键，与 boq_item.match_key 一致 |
| `match_key_source` | Selection | ✅ | dict/std/code/raw |
| `std_name` | Char(512) | ✅ | 标准化名称 |
| `std_spec` | Char(512) | ✅ | 标准化规格 |
| `material_dict_id` | M2O → material.dict | ❌ | 物料分类关联 |
| `unit_std` | Char(32) | ✅ | 归一化单位 |
| `avg_rate` | Float(16,6) | ❌ | 历史均价（completed 行） |
| `min_rate` / `max_rate` | Float(16,6) | ❌ | 历史区间 |
| `sample_count` | Integer | ❌ | 参与统计的 completed 行数 |
| `latest_price` | Float(16,6) | ❌ | 最新一条 completed 行的单价 |
| `latest_period` | Date | ❌ | 最新价格期 |
| `latest_source` | Char(512) | ❌ | 最新记录来源（工程名） |
| `embedding_version` | Integer | ❌ | 同步版本计数器，每次重建 LanceDB 索引 +1（用于检测漂移） |
| `vector_sync_pending` | Boolean, 默认 False | ❌ | **【v1.2 新增】PG 已更新但 LanceDB 向量未同步标记**（写 PG 成功、向量失败时的补偿位点，见 §5.6） |
| `migration_batch_id` | M2O → import.batch | ❌ | 迁移批次溯源 |
| `active` | Boolean, 默认 True | ✅ | 软删除标记 |
| `created_at` | Datetime, 默认 now | ✅ | 首次迁入时间 |
| `updated_at` | Datetime | ✅ | 最后更新时间 |

> **⚠️ embedding 不存 PG**：成本库的向量 embedding 完全由 LanceDB 外部管理（§五），PG 表**不含 embedding 向量字段**。`embedding_version` 仅记录同步版本号，用于检测"PG 与 LanceDB 是否同步"，不存向量本身。

**索引**：`match_key`（UNIQUE）、`std_name`（GIN trigram）、`unit_std`。

### 3.3 match_key 与 boq_item 的关系

| 关系 | 说明 |
|---|---|
| 一对多 | 一条 cost_catalog 对应多条 boq_item（同一 match_key 的不同工程记录） |
| 不可反向 | cost_catalog 不含 boq_item 的行级细节（如 sequence、provisional_sum） |
| 同步策略 | cost_catalog 不从 boq_item 自动同步，由迁移向导手动触发（防污染） |
| 溯源 | cost_catalog 的 `latest_source` 指向具体 boq_item 的 `import_batch_id` |

## 四、迁移策略（boq_item → cost_catalog）

### 4.1 触发条件（M3 §7 评估门槛）

只有满足以下条件时，才建议启动迁移：

| 条件 | 阈值 | 检查项 |
|---|---|---|
| 标准化覆盖率 | ≥ 80% | `material_dict_id` 非空 / `std_name` 非空 的行数占比 |
| 异常率 | < 10% | `anomaly_flag='error'` 行数占比 |
| completed 占比 | ≥ 60% | `data_source_type=completed` 行数占比 |
| match_key 质量 | 优先级 1+2 ≥ 80% | dict/std 生成的 match_key 占比 |

**不满足条件时**：M3 的数据质量仪表盘显示 ❌，建议先完成数据治理（run rapidfuzz 匹配向导补标准化），**不启用迁移**。

### 4.2 迁移规则

**聚合逻辑**（对每条 match_key）：

```python
def migrate_match_key(match_key):
    # 1. 取该 match_key 下所有 active=True + data_source_type=completed 的 boq_item
    candidates = boq_item.search([
        ('match_key', '=', match_key),
        ('active', '=', True),
        ('data_source_type', '=', 'completed'),
        ('unit_rate_num', '!=', False),
    ])
    
    if not candidates:
        return None  # 无 completed 数据，跳过
    
    # 2. 计算统计量
    rates = [c.unit_rate_num for c in candidates]
    avg_rate = sum(rates) / len(rates)
    min_rate = min(rates)
    max_rate = max(rates)
    
    # 3. 取最新一条（按 price_period 降序）
    latest = candidates.sorted(lambda x: x.price_period, reverse=True)[0]
    
    # 4. 写入 cost_catalog
    return {
        'match_key': match_key,
        'std_name': latest.std_name or latest.item_name,
        'std_spec': latest.std_spec or latest.item_feature or '',
        'material_dict_id': latest.material_dict_id.id,
        'unit_std': latest.unit_std,
        'avg_rate': avg_rate,
        'min_rate': min_rate,
        'max_rate': max_rate,
        'sample_count': len(rates),
        'latest_price': latest.unit_rate_num,
        'latest_period': latest.price_period,
        'latest_source': latest.project_name,
    }
```

**去重规则**：
- 同一 match_key 只保留一条 cost_catalog 记录
- 更新时**覆盖数值字段**（avg/min/max/latest），**保留人工标注**（std_name/std_spec/material_dict_id 如果已有则不覆盖）
- 迁移后原 boq_item **不被修改或删除**（boq_item 仍是数据源，cost_catalog 只是视图层聚合）

### 4.3 迁移向导流程

```
Step 1: 选择迁移范围
  - 全部 match_key（批量）
  - 指定 match_key 前缀（如 "dict:" 前缀的）
  - 手动勾选若干 match_key

Step 2: 预览（不写库）
  - 展示 N 条 match_key 将迁移
  - 每条显示：match_key / std_name / sample_count / avg_rate / min-max 区间
  - 异常提示：样本数 < 3 的 match_key 标黄（统计不可靠）

Step 3: 确认迁移
  - 二次确认："本次将迁入 N 条 cost_catalog 记录，确认？"
  - 写 audit_log（action='migration'）

Step 4: 执行迁移
  - 调用 cost_migration.migrate()
  - 写入 cost_catalog（upsert：存在则更新数值，不存在则新建）
  - 返回迁移结果摘要

Step 5: 生成 embedding
  - 对每条迁入的 cost_catalog，调用 embedding 服务生成向量
  - 写入 LanceDB（外部，不写入 PG）
  - 异步处理，避免阻塞
```

### 4.4 迁移后行为

| 行为 | 说明 |
|---|---|
| boq_item 不变 | 原记录保持不动，继续参与统计和溯源 |
| cost_catalog 标准化字段只读 | `std_name/std_spec/material_dict_id` 属 **B 类不可重建字段**（M1 §4.9），迁移入库后**不开放直接编辑**；如需修正，走专用向导并强制填写 reason 审计（同 M3 §6 异常标注机制） |
| cost_catalog 数值字段可刷新 | `avg/min/max/latest` 等数值由迁移触发重新计算（提供「刷新」按钮） |
| 重新导入触发重迁移 | 新的 boq_item 导入后，cost_catalog 的统计量需要重新计算（提供「刷新」按钮） |

> **⚠️ 为什么标准化字段不设 writable**：M1 §4.9 将 `std_name/std_spec/material_dict_id` 划为 **B 类不可重建字段**，任何变更必须走专用向导 + reason 必填 + 审计日志。若 cost_catalog 的标准化字段开放编辑，会绕过该机制，造成无法追溯的数据漂移（风险 R7）。因此 cost_catalog 的 B 类字段继承 M1 的安全约束。

## 五、LanceDB 向量语义检索【P2】

### 5.1 架构位置

LanceDB 作为**外部独立文件向量库**，不侵入 PG：
- embedding 生成：Python 服务层
- 向量存储：LanceDB 本地 `.lance` 文件
- 查询：Python 服务层调用 LanceDB API
- 结果回灌：写入候选列表，供语义匹配向导使用

### 5.2 目录结构

```
zaojia_boq/
  services/
    vector_search_service.py      # LanceDB 封装
    embedding_service.py          # embedding 模型封装
  data/
    lance_db_path.txt             # LanceDB 数据目录路径（配置项）
```

### 5.3 embedding 模型选型（P2 评估，M4 默认占位）

| 方案 | 维度 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **Sentence-BERT（本地）** | 768 | 零依赖、离线可用 | 中文效果一般 | **M4 默认** |
| **text-embedding-3-small（OpenAI）** | 1536 | 效果好、支持多语言 | 需 API Key、有费用 | P2 可选升级 |
| **bge-m3（开源）** | 1024 | 中文效果好、本地可用 | 模型较大（~2GB） | 后续评估 |

**M4 默认实现**：Sentence-BERT `sentence-transformers/all-MiniLM-L6-v2`（768 维，约 80MB），满足"同一类材料名称相似"的召回需求。

### 5.6 PG ↔ LanceDB 一致性协议【v1.2 新增 · 中等风险项补强 · 条件性】

> **【v6.5 条件性】** 本节约在 **LanceDB 被确证启用**时才需要（启用门槛见 架构 §十二：rapidfuzz+字典召回率不达标 且 规模确实需要）。在默认路径（不引入向量检索）下**不存在双源，本协议不适用**，PG 单一真相源即可。下面内容作为「若启用」的预案保留。

**问题背景（中等风险项）**：PostgreSQL 与 LanceDB 是两套独立存储，**不存在跨系统的原子事务**。一笔 `cost_catalog` 记录的变更，若 PG 写成功、向量写失败（或反之），就会出现「PG 有、LanceDB 没有」或「LanceDB 有、PG 没有」的不一致。审计与统计以 PG 为准时会漏召回，以向量为准时会召回已删除项。必须显式约定一致性边界与补偿机制，不得假设「写两次都成功」。

**五大机制**：

| 编号 | 机制 | 规则 | 兜底 |
|---|---|---|---|
| ① 写序 | **PG 为真相源（source of truth）** | 任何数据变更一律先写 PG（含 `write_date`）；向量同步在 PG 事务提交**之后**异步触发 | 即使向量同步挂掉，PG 数据完整、可重新全量重建向量 |
| ② 幂等 upsert | 向量主键 = `match_key`（或 `cost_catalog.id`） | LanceDB `merge_insert` 按主键 upsert；同一 `match_key` 重复同步不产生重复向量 | 重试安全，可任意次重跑而不膨胀 |
| ③ 补偿位点 | 新增 `vector_sync_pending`（Boolean，默认 False） | PG 写成功后置 `True`；向量 upsert 成功后置 `False`；失败时保持 `True` 留待重试 | `reconcile_vectors()` 扫描 `pending=True` 重试；页面可显示「待同步数」告警 |
| ④ 孤儿向量清理 | 删除/失效记录必须清理其向量 | `active=False` 或 `orphaned=True` 的 `cost_catalog`，其 LanceDB 向量须 `delete`；重导后孤儿行同理 | `reconcile_vectors()` 比对「PG 有效 id 集合」vs「LanceDB 现有 id 集合」，差集中的孤儿向量删除 |
| ⑤ 漂移检测 | `embedding_version`（Integer 计数器） | 每次重建索引/模型升级 +1；向量记录携带 `embedding_version`；检索时校验查询向量的 version 与库内一致 | version 不一致 → 标记该 match_key 需重建，触发全量或增量重算 |

**`reconcile_vectors()` 对账任务（设计，未实现）**：
```python
def reconcile_vectors(self):
    # 1. 补偿：重试所有 pending
    pending = self.search([('vector_sync_pending', '=', True)])
    for rec in pending:
        ok = vector_search_service.upsert(rec)   # ② 幂等
        if ok:
            rec.vector_sync_pending = False

    # 2. 孤儿清理：PG 已失效的 match_key，其向量删除 ④
    alive_keys = set(self.search([('active', '=', True)]).mapped('match_key'))
    orphan_vecs = vector_search_service.keys_not_in(alive_keys)
    vector_search_service.delete(orphan_vecs)

    # 3. 漂移检测：库内 version 与当前模型不一致则标记重建 ⑤
    current_ver = self.env['ir.config_parameter'].get_param('embedding_version')
    mismatched = vector_search_service.keys_with_version_ne(current_ver)
    for k in mismatched:
        rec = self.search([('match_key', '=', k)], limit=1)
        if rec:
            rec.vector_sync_pending = True   # 回到补偿流程重算
```

**诚实边界**：本协议保证「最终一致」，不保证「实时一致」。语义检索结果**必须标注来源=语义**并提示「可能存在同步延迟」；关键审计口径一律以 PG 聚合值为准，不得用向量检索结果替代统计。

## 六、语义匹配向导

### 6.1 定位与触发

**触发条件**：用户在"快速匹配"界面，除了 rapidfuzz 关键词召回外，额外启用"语义匹配"按钮。

**与 rapidfuzz 的区别**：

| 维度 | rapidfuzz | LanceDB 语义 |
|---|---|---|
| 原理 | 字符串编辑距离 | 语义向量相似度 |
| 适用场景 | 名称写法略有不同 | 名称差异大但实际同物（如"电缆"vs"电力电缆"） |
| 速度 | < 100ms | ~200-500ms（含 embedding 生成） |
| 精度 | 高（精确匹配优先） | 中（语义相近召回） |
| 互斥 | — | 两者**同时召回、合并排序** |

### 6.2 召回合并逻辑

```python
def combined_match(std_name, material_dict, top_k=5):
    # 1. rapidfuzz 召回 Top-5
    keyword_results = rapidfuzz_match(std_name, material_dict)
    
    # 2. LanceDB 语义召回 Top-5
    semantic_results = vector_search.search(std_name, top_k=5)
    
    # 3. 合并去重（按 match_key）
    all_results = merge_dedup(keyword_results, semantic_results)
    
    # 4. 加权排序
    # rapidfuzz 分数保留原值
    # LanceDB 分数归一化到 0-100 再加权
    scored = rank_combined(all_results)
    
    return scored[:top_k]
```

**最终候选列表**显示：名称 / 规格 / 来源（rapidfuzz / 语义）/ 综合分数 / 分类路径。

### 6.3 边界情况

| 情况 | 处理 |
|---|---|
| LanceDB 为空（首次使用） | 静默跳过语义召回，只用 rapidfuzz |
| 无候选（两者均无结果） | 提示"未找到匹配，请手动建立字典项" |
| 语义召回与关键词召回重复 | 去重，只显示一条（按 `match_key` 合并） |
| embedding 生成失败 | 标记 warning，该条不入库成本库，保留原 cost_catalog 记录 |

## 九、风险登记册

| 编号 | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| R1 | cost.catalog 数据过时 | 均价失准 | 迁移后提供「刷新」按钮；新导入批次后提示重新迁移 |
| R2 | embedding 模型效果差 | 语义召回不准 | 默认 Sentence-BERT 效果有限；支持升级 OpenAI embedding；召回结果标注"语义"来源供用户判断 |
| R3 | LanceDB 文件损坏 | 语义检索失效 | LanceDB 文件定期备份；重建索引可全量重跑 |
| R4 | 迁移误操作覆盖已有 cost_catalog | 人工精炼丢失 | 迁移时保留已有 std_name/std_spec，只更新数值字段 |
| R5 | 迁移门槛误判（达标但数据仍有问题） | 迁移后 cost.catalog 质量差 | M3 仪表盘显示详细分布，管理员人工复核后再执行迁移 |
| R6 | embedding 文本拼接不当 | 检索效果差 | 提供可配置的拼接模板（默认 "std_name std_spec"），管理员可调 |
| R7 | cost.catalog 与 boq_item 数据漂移 | 统计口径不一致 | 迁移后 cost.catalog 独立维护，不自动同步；明确标注"此数据来自 X 日迁移，非实时更新" |
| **R8** | **cost_catalog B类字段绕过审计** | 标准化字段被静默修改，无法追溯 | cost_catalog 的 `std_name/std_spec/material_dict_id` 继承 M1 B类字段约束，**不开放直接编辑**；修正走专用向导 + reason 必填（见 §4.4 修正说明） |
